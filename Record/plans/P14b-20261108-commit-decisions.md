## 为什么不能照旧稿直接接线

- 取消前检查会话身份，只能拒绝尚未开始的写入。剪贴板 SetContent/Flush 与历史 PNG/JSON/修剪已经开始后，没有原子回滚接口。
- 全屏旁路含等待与恢复前景窗口；会话失效后，晚到清理不能抢回新取景会话的焦点。未来实施必须独立保护旁路所有权。
- Core 的终态、收尾原因与 CaptureResult.Failure 是三个概念。不能把新枚举已落地说成 App 已统一，也不能把附属写入失败全部改成 failure=None。

## 建议确认的五项

| 项 | 建议 | 明确边界 |
|---|---|---|
| 1 互斥与优先级 | 取景中忽略快捷全屏；快捷取图尚未进入提交时，F1 可取消它并立即打开取景。不排队，不重复采集。 | 已获提交权、开始写剪贴板/历史后，不再取消该提交；这段时间的 F1 忽略且不排队，结束后可再次按F1。该短阶段时长需真实交互验收，不能宣称≤5ms。 |
| 2 失败留痕 | 没有成功图像时，不新增历史条目；失败原因留在日志与 CaptureResult。 | 不把黑图/空图写历史，不为失败扩展现有历史 JSON 状态字段。 |
| 3 退出收尾 | 使尚未提交的会话失效并尽力清理，退出最多额外等300ms，不等待不可控采集线程。 | 300ms 是拟定等待上限，不是线程必定退出或写入必定撤销保证；已开始的提交只能尽力完成，不启动替代截图。 |
| 4 分类兼容 | 保持现有常规历史分类和 ScreenQuick 元数据，Origin 使用 Normal，不新增 Monitor 枚举。 | 此为兼容选择；不重写旧历史、不取消 P14c version2 的来源信息。 |
| 5 附属写入失败 | 图像成功仍按采集 Completed 收尾，但分别记录 ClipboardFailed/HistoryFailed，用户提示保留现状。 | 不能写成 failure=None 掩盖错误；Completed 不代表剪贴板和历史均成功，不能以 CaptureResult.IsSuccess 替代完整状态判断。 |

## 技术实施的先决条件（不需要另增产品功能）

1. 一个会话槽与显式 surface；Quick 不触发取景专属 Hotkey.EndCaptureMode/NotifyOverlayClosed。
2. 提交权与取消/新会话开槽共用同步边界；写入阶段不可被旧会话 End 误清忙标。进入提交前身份、有效性与所有权全部有效。
3. 失效后的取图只释放载荷，不能写入、提示成功或执行晚到的前景恢复。不得用无限等待或杀用户进程实现取消。
4. 保留刷新报告列出的6条保护日志与其输出顺序；App ParseEndReason/TerminalStateFor 与 Core 两新原因一并接齐。
5. 全量隔离构建、Core.Tests 与格式验证后，再交主人验证真实F1/F2交错与退出。构建不触碰当前默认运行bin/obj，不启动App/smoke。
